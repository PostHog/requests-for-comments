# Request for comments: Wizard v2.5

## Problem statement

What is the ideal shape for a Wizard shape today? 

What is an ideal shape for the Wizard in Q4 2026?

It's certainly not the same as it was in 2024/2025. The assumptions and limitations that shaped the Wizard today is _not_ applicable anymore.

I'm here to challenge our assumptions, propose some changes today, and prospect about the future shape of the Wizard.

> This is the near-term half. The full rethink lives in [Wizard v3](./2026-07-24-wizard-v3.md).
> V2.5 ships this quarter. V3 is forward looking and ships in future.


## The old assumption

The benchmark to beat in 2025 was an engineer reading our docs and trying to setup PostHog for Product Analytics themselves. The 2025 goal was simple: _get as many ingested, identified events into PostHog as possible_. 

This is outdated in several ways:
- Product Analytics is no longer the default assumed entry point
- We're pushing to get people on to self-driving
- The quality bar of an install has changed. Users (that are our ICP) are agent pilled and have Opus 5.

The target has shifted. We can't keep shooting the same shot and hope it'll land.

I'm wary of complacency. I'm wary that we're afraid to swing big because we have something that works and people use. But if we're repositioning entirely around self-driving and believe the ICP has shifted, maybe we can and should swing bigger.

## Some historical context

The limitations that shaped the Wizard V2 are also no longer relevant. 

Models were weak, they were expensive, most people weren't agent pilled. In fact, "Agent" was an ill defined and controversial term.

### The old goal post

We wanted the Wizard to feel like a traditional "installation wizard" with extra magic.

The Wizard V2 did precisely these things:
- Detect what framework the user was using
- Pull docs, skills, packaged examples and context.
- Plan ~15 events to collect from the user's project
- Install the SDK
- Initialize the SDK and pull down relevant environment variables
- Enable auto-capture, error tracking, and session replays
- Instrument 15 capture call sites
- Create 5 insights and a dashboard.
- Hand off with a markdown report for humans and robots alike.
- Taught people about PostHog through our slides show
- Brought joy with things like a Hackernews tab

This was great for its time.

The PR made sense for our goals, the PR was small enough to test, it got people off a blank page.

In 2025, most people were **integrating PostHog by hand** still. The Wizard will beat that every time, hands down.

But _most_ developers are armed with GPT 5.6 and Opus 5 class models today. There is honestly a less clear advantage to using the Wizard in its current form.

### The old limitations

We also needed the Wizard to be cheap, relatively fast, and reliable. When all we had to lean on were Opus 4.5 and Sonnet 4.5, a linear agent with heavy scope restrictions was all that we could do. This was also with 200K context.

- These models failed miserably without specific guidance to integrate PostHog
- They could not reason about the complexities of SSR, Next App vs Page router, React Native vs React, so on.
- We could not run them fast and cheap enough to add interactivity
- We could not guarantee the integration quality without hand holding the robot.
- Oh, monorepos were much less feasible
- We could not practically introduce interactivity, especially not cheaply, safely and reliably.

The most prominent pieces of feedback we get are "make the wizard support monorepo" and "make the setup customizable". We've wanted to do these things, they were not practical until very recently.

### What recent models unlock

With newer models, especially the GPT 5.6 class models, all of these practical limitations are gone.

We can run the Wizard V2 shape for 1/3 the cost and 1/2 the time.

Actual numbers from a live flagged experiment, on production sized apps: 

| step | pi p50 | anthropic p50 |
| --- | --- | --- |
| seed | 0:21 | 0:43 |
| init | 0:42 | 2:43 |
| install | 0:22 | 0:29 |
| capture | 1:14 | 5:25 |
| identify | 0:46 | 2:21 |
| error-tracking | 0:22 | 1:29 |
| build | 0:54 | 2:11 |
| review | 1:55 | 4:49 |
| dashboard | 0:27 | 1:23 |
| report | 0:41 | 3:28 |
| total (median run) | 7:58 (n=511) | 26:01 (n=85) |

What would have taken us 26 minutes to run now takes less than 8 and costs ~$2.

I believe that it's time for a big rethink. The assumptions and limitations under which the Wizard V2 was built no longer hold. It's time to throw away the set of skills and tasks that were designed under a different set of assumptions and limitations.

It is now practical to build a multi-agent wizard setup with newer models. It _can_ do the same old Wizard V2 task just fine. In fact it beats the old Wizard in [7/11 open source apps](https://github.com/PostHog/context-mill/pull/245#issuecomment-5024035756) we benchmarked. But _**should it still do these same old things?**_

## Issues with Wizard V2 (The current Wizard)
### The Wizard isn't shaped for self-driving

A year ago, the singular most important goal -> give everyone autocapture, session replays, a handful of events, and a dashboard.

This isn't the case anymore. For self-driving, we need to:
- Install the SDK across the repo (22% of the time monorepos)
- Identification (some things never change) and group analytics
- Enable all the features, like autocapture, session replays, error tracking, AIO, so on.
- Connect data sources
- Connect signal sources
- Scouts
- Bring you to PostHog to see the PRs flow
- **Ask questions along the way to customize this setup**

If we are fully committing to self-driving, this is the flow we'd want to implement.

Then there's cloud runs. This _is_ gonna be the fastest way to get to self-driving. Nothing beats a single-click setup that leads directly to a PR. This requires us to have that same autonomous experience, but with the questions to ask up front.

This default Wizard program isn't the right shape for a self-driving-first PostHog. 

### The Wizard assumes users want Product Analytics (and isn't in a monorepo)

What if they're not here for self-driving? Well, again, we need to ask.

PostHog has many ~products~ tools. The Wizard should ask the user which tool they want to use, then set it up for them.

If a user is here for AIO, why are we setting up 15 events for them?

We also don't handle monorepos well. We just assume the first front-end-client-side-shaped project is the one they want to instrument and set it up for them. In practice, agentic detection analytics shows that `22.2%` of users are using monorepos.

We don't handle any of these things well.

### The integration quality isn't that good anymore

Today, the Wizard does these things:
- Install the SDK
- Add environment variables
- Hook up identification
- Enable session replays, autocapture, and error tracking
- Adds ~15 events
- 5 insights and a dashboard.

When this was decided, it was exceptional because the benchmark to beat was an engineer reading our docs and adding the PostHog SDK, and then deciding what events to track and how to set up the dashboard.

The problem is, people have Fable now.

By comparison, the Wizard didn't leave projects in a ready to run state for [7/11 open source apps](https://github.com/PostHog/context-mill/pull/245#issuecomment-5024035756) that we ran against.

We leave behind many events like `viewed about page` and `clicked sign up`. We built simple insights and dashboards with these. 

There's also practical niceties like:
- A const file with all event definitions
- Event schemas
- Using PostHog through a wrapper (often the preferred shape)
- Group analytics
- Reverse proxies

Once again, these were great compared to an empty project and manual hookups. 

These are significantly less useful if you look at what someone with Opus 5 or Fable can do with our docs. 


-> We'll ship some big changes to realign with what users need today in **Wizard V2.5**.
-> We hope to ship even bigger things in **Wizard V3** that fundamentally challenges the way the Wizard works with users today.

## What is Wizard v2.5?

The scope of Wizard V2.5 is deliberately scoped to immediate requirements. Specifically,

- Focus on immediate, big unlocks
- Reshaping the context to fit our new orchestrator mental model
- Taking most of the low hanging fruits of an orchestrator model
- Ship Q3 2026

## What we're gonna fix now (Wizard v2.5)

1. Cut back what the default Wizard command does
   - Install the SDK
   - Initialize and apply environment variables
   - Instrument basic identify
   - instrument all of the base 4 products like Product Analytics, Web Analytics, Session Replay, and Error Tracking
   - Enable all the features self-driving tries to enable.
   - Write a handoff report for their agent locally, handoff to a handbook in PostHog
    - Suggest captures, funnels, dashboards, insights, etc.
    - Leave behind context for the agent to use the PostHog MCP
    - Suggest data sources to connect
    - Leave commands + links to skills to do things like add new data sources, upload source maps, etc.
    - **Key removals**: 15 capture sites, dashboards, insights. This isn't relevant, leave the tools for their agents to drive these.
    - **Advantage is speed**: All this work can be done fast enough where we don't lose their attention. I truly believe we can get this in 3-5 minutes tops.
2. Force MCP install on the outro and cut out the rest
  - It's Q3 2026 and we're self-driving. Of course they need this
  - We don't need to ask, just install everywhere.
  - I'm convinced we should ask about Slack and show the tutorial elsewhere
3. Last but not least, only handoff screen is: "Do you want self-driving?"
  - On yes, we run that program immediately
  - On Cloud run -> They could be taken to a web UI first experience
  - We can teach them what this means with a show. We're good at shows.
4. Handle monorepos
   - We need orchestration.
   - Because we omit captures, we can have Cloud runs rerun this for every monorepo site they select.
5. Cloud runs
   - Repo scanning command with `npx @posthog/wizard scaffold` to just do monorepo/project structure detection and understand what products are relevant.
   - Run this _immediately_ after someone connects their repo. Can be reused for rest of wizard.
   - Uploads this information into PostHog. This info is useful _everywhere_

All of this should take a week or two. Maybe we'll break a few things and drop a few people, but its fine. We'll lose more people by not shipping this more relevant experience sooner.

## What we'll fix in the future (Wizard V3)

Everything else lives in the [Wizard v3 RFC](./2026-07-24-wizard-v3.md):

1. Self-driving first experience
2. Customizable, modular setup
3. Option to defer to the user's agent
4. Higher instrumentation quality
