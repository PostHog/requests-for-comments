# Request for comments: Wizard v3

## Problem statement

The Wizard's shape from 2025 is showing age. 

The target has shifted.

The benchmark to beat was an engineer reading our docs and trying to setup PostHog for Product Analytics themselves.

This is outdated in several ways:
- Product Analytics is no longer the default entry point
- We have self-driving
- The quality bar of an install has changed. Users (that we are targetting) are agent pilled and have Fable.

The limitations that shaped the Wizard V2 are also no longer relevant. We needed it to be cheap, relatively fast, and reliable. When all we had to lean on were Opus 4.5 and Sonnet 4.5, a linear agent with heavy scope restrictions were all that we could do.

I believe that it's time for a big rethink. The assumptions and limitations underwhich the Wizard V2 was built no longer hold. It's time to throw away the set of skills and task that were design under a different set of assumptions and limitations.

## Issues of Wizard V2
### Limitation 1 – The Wizard doesn't handle self-driving well

A year ago, this was true. People wanted Product Analytics. That was the singular most important goal -> give everyone autocapture, session replays, a handful of events, and a dashboard.

This isn't the case anymore. For self-driving, we need to:
- Installed SDK across the repo
- Identification (some things never change) and group analytics
- Enable all the features, like autocapture, session replays, error tracking, AIO, so on.
- Connect data sources
- Connect signal sources
- Scouts
- Bring you to PostHog to see the PRs flow

This requires _2_ wizard commands. Oof.

Then there's cloud runs. This _is_ gonna be the fastest way to get to self-driving. Nothing beats a single-click setup.

This default Wizard program isn't the right shape for a self-driving-first PostHog. 

### Limitation 2 – The Wizard assumes users want Product Analytics (and isn't in a monorepo)

What if they're not here for self-driving? Well, again, we need to ask.

PostHog has many ~products~ tools. The Wizard should ask the user which tool they want to use, then set it up for them.

We also don't handle monorepos well. We just assume the first front-end-client-side-shaped project is the one they want to instrument and set it up for them. In practice, agentic detection analytics shows that `22.2%` of users are using monorepos.

We don't handle any of these things well.

### Limitation 3 – The integration quality isn't that good anymore

Today, the Wizard does these things:
- Install the SDK
- Add environment variables
- Hook up identification
- Enable session replays, autocapture, and error tracking
- Adds ~15 events
- 5 insights and a dashboard.

When this was decided, it was exceptional because the benchmark to beat was an engineer reading our docs and adding the PostHog SDK, and then deciding what events to track and how to set up the dashboard.

The problem is, people have Fable now.

By comparison, the Wizard didn't leave projects in an ready to run state for [7/11 open source apps](https://github.com/PostHog/context-mill/pull/245#issuecomment-5024035756) that we ran against.

We leave behind many events like `viewed about page` and `clicked sign up`. We built simple insights and dashboards with these. 

Once again, these were great compared to an empty project and manual hookups. 

These are significantly less useful if you look at what someone with Opus 5 or Fable can do with our docs. 

## Why we couldn't do this before

We've been eyeing up a way to have multi-agent wizard setups for a while. We need it for customizable set ups, we need it for interactivity, and we need it to keep up with the fast changing shape of PostHog and PostHog's users.

We struggled to do this with the Anthropic Agent SDKs. Its caching structure, terrible start up time, and cost/speed limited us from trying. You're actually punished if you break up the agent into multiple sub-agents. The cache writes cost 12x as much as cache reads, and the time it takes for that agent to start up is significant on a busy day.

With newer models, especially the GPT 5.6 class models, all of these limitations are gone.

We can run the Wizard V2 shape for 1/3 the cost and 1/2 the time.

By the time a Sonnet 4.6 agent boots up, GPT 5.6 Luna can finish installing and initialize the SDK.

We can now have multiple, faster, cheaper agents do the work we need in a parallelizable, modular way. This just means we can do more, we can ask more questions, and we can fundamentally change the shape of the Wizard.

![](../images/2026-07-24-wizard-v3/agent-dags-waves.png)

This means we can handle these things we could not before:
- Instrument what the user needs by enqueuing specialized agents for each job
- We can be flexible, self-driving users and analytics users are here for different things, we _can_ handle both
- The instrumentation quality _can_ be much better. We can challenge the goal post we set under different limitations and expectations.

## What makes a Wizard V3?

1. Self-driving first experience
2. Customizable, modular setup
3. Option to defer to the user's agent
4. Higher instrumentation quality

### 1. Self-driving first experience

`@npx @posthog/wizard@latest` should do the following:
- Install the SDK
- Initialize it and hook up environment variables
- Identify your users
- Turn on all the features for self-driving
- Ask you about external signal sources
- Design and offer scouts to you
- Kick you to PostHog Desktop or the Inbox.
- Leave lots of useful context for _their_ agents to take over.

For a self-driving users, this is what's needed to get started. We can assume they're AI pilled, they have their own agents, and they are comfortable with using the PostHog through the MCP.

They don't need all the fluff on top. This _is_ just the thing we offer them.

For **cloud runs**, we can surface all of these questions early and during the run, and just pass this information to the agent.

This shape will change. Self-driving itself is fast changing. The new modular, multi-agent flows are flexible enough to adapt to these changes.

### 2. Customizable, modular setup

During onboarding, we already ask questions about which tools the user wants to use, what features they want to enable, and how they want to use the PostHog.

We need to honor this.

Users in 2025 did not expect or understand this new, agent driven experience. By not asking them questions and giving them choices, we avoided confusion and got them off an empty page faster. 

This is no longer true, we can give them a better experience:

- (Agent) We scan your repo, ask you which projects to instrument (10s)
- (User) You tell us which projects and products you want to instrument
- (Agent) Plans the flow and enqueues agents to instrument your projects (15s)
- (Agent) We add and initialize the SDKs and hook up environment variables (30s - 1 min)
    - At this point, you can just leave and you'll have a working setup to continue with your agent. You _can_ just leave.
- (User) We pause after installing the SDKs, we ask you about features and teaches you about them.
  - Do you want group analytics and what are the cohorts/groups you have? 
  - What questions are you trying to answer with your product analytics integration? 
  - Do you want to connect data warehouse sources? 
  - Do you want self driving? (Do you know what it is???)
  - Do you want some dashboards to start with?
  - Do you want us to install PostHog Desktop?
- (Agent) We move on to instrument what you agreed to, probably as you say yes or no to our tools. (3 minutes)
- (Agent) Then, once we're done, we ask to clean up after ourselves, review our changes, and leave context for your agent. This takes can take 5+ minutes. That's fine, leave us running, we'll handle the rest.

### 3. Option to defer to the user's agent
We cannot really compete with Fable class models. That's fine. What if we offer that as an option? A basic installation.

There are things we can do for you still:
- Install
- Environment variables
- Enabling features
- Hooking up identification (I'm convinced _we_ can do this uniquely lol)
- Leaving skills for your agent
- Leave meaningful instructions as handoff.

### 4. Higher instrumentation quality
 
What do you care about?

Yes you, the user.

Have no opinions? We'll scan your repo, hook up events for the core flows (and more than before) and set up insights and dashboards. Even leave suggestions for your agents.

Have opinions? You mainly care about sign up conversion and time to checkout? We can do that for you, too.

We'll finish with a GPT 5.6 Sol class audit. This, alone, turns 4/11 projects capturing successfully post instrumentation after a wizard run to 11/11. In our tests, this gives us 13% higher ingestion rate after a Wizard run in the same period.

We can do this because GPT 5.6 Sol class models are faster, cheaper, and more capable than anything practical before.

## The timeline

I think we can and need to do this over the next quarter or so. All the prep work to make this Wizard redesign possible is already done. 

The targeted has shifted too far away from what we design the V2 Wizard to do. 

The Wizard adapts, or we become obsolete.
