# Request for comments: Wizard v2.5 and v3

## Problem statement

What does a perfect Wizard integration look like in Q3 2026?

I don't know, but it's no longer the 2025 shape we built for.

The benchmark to beat in 2025 was an engineer reading our docs and trying to setup PostHog for Product Analytics themselves. The 2025 goal was simple: _get as many ingested, identified events into PostHog as possible_. 

This is outdated in several ways:
- Product Analytics is no longer the default assumed entry point
- We're pushing to get people on to self-driving
- The quality bar of an install has changed. Users (that are our ICP) are agent pilled and have Opus 5.

The target has shifted. We can't keep shooting the same shot and hope it'll land.

I'm wary of complacency. I'm wary that we're afraid to swing big because we have something that works and people use. But if we're repositioning entirely around self-driving and believe the ICP has shifted, maybe we can and should swing bigger.

## Some historical context

The limitations that shaped the Wizard V2 are also no longer relevant. 

Models were weak, they were expensive, most people weren't agent pilled. In fact, "Agent" was an ill defined and controversial term.

### The old goal post

We wanted the Wizard to feel like a traditional "installation wizard" with extra magic.

The Wizard V2 did precisely these things:
- Detect what framework the user was using
- Pull docs, skills, packaged examples and context.
- Plan ~15 events to collect from the user's project
- Install the SDK
- Initialize the SDK and pull down relevant environment variables
- Enable auto-capture, error tracking, and session replays
- Instrument 15 capture call sites
- Create 5 insights and a dashboard.
- Hand off with a markdown report for humans and robots alike.
- Taught people about PostHog through our slides show
- Brought joy with things like a Hackernews tab

This was great for its time.

The PR made sense for our goals, the PR was small enough to test, it got people off a blank page.

In 2025, most people were **integrating PostHog by hand** still. The Wizard will beat that every time, hands down.

But _most_ developers are armed with GPT 5.6 and Opus 5 class models today. There is honestly a less clear advantage to using the Wizard in its current form.

### The old limitations

We also needed the Wizard to be cheap, relatively fast, and reliable. When all we had to lean on were Opus 4.5 and Sonnet 4.5, a linear agent with heavy scope restrictions was all that we could do. This was also with 200K context.

- These models failed miserably without specific guidance to integrate PostHog
- They could not reason about the complexities of SSR, Next App vs Page router, React Native vs React, so on.
- We could not run them fast and cheap enough to add interactivity
- We could not guarantee the integration quality without hand holding the robot.
- Oh, monorepos were much less feasible
- We could not practically introduce interactivity, especially not cheaply, safely and reliably.

The most prominent pieces of feedback we get are "make the wizard support monorepo" and "make the setup customizable". We've wanted to do these things, they were not practical until very recently.

### What recent models unlock

With newer models, especially the GPT 5.6 class models, all of these practical limitations are gone.

We can run the Wizard V2 shape for 1/3 the cost and 1/2 the time.

Actual numbers from a live flagged experiment, on production sized apps: 

| step | pi p50 | anthropic p50 |
| --- | --- | --- |
| seed | 0:21 | 0:43 |
| init | 0:42 | 2:43 |
| install | 0:22 | 0:29 |
| capture | 1:14 | 5:25 |
| identify | 0:46 | 2:21 |
| error-tracking | 0:22 | 1:29 |
| build | 0:54 | 2:11 |
| review | 1:55 | 4:49 |
| dashboard | 0:27 | 1:23 |
| report | 0:41 | 3:28 |
| total (median run) | 7:58 (n=511) | 26:01 (n=85) |

What would have taken us 26 minutes to run now takes less than 8 and costs ~$2.

I believe that it's time for a big rethink. The assumptions and limitations under which the Wizard V2 was built no longer hold. It's time to throw away the set of skills and tasks that were designed under a different set of assumptions and limitations.

It is now practical to build a multi-agent wizard setup with newer models. It _can_ do the same old Wizard V2 task just fine. In fact it beats the old Wizard in [7/11 open source apps](https://github.com/PostHog/context-mill/pull/245#issuecomment-5024035756) we benchmarked. But _**should it still do these same old things?**_

## Issues with Wizard V2 (The current Wizard)
### The Wizard isn't shaped for self-driving

A year ago, the singular most important goal -> give everyone autocapture, session replays, a handful of events, and a dashboard.

This isn't the case anymore. For self-driving, we need to:
- Installed SDK across the repo (22% of the time monorepos)
- Identification (some things never change) and group analytics
- Enable all the features, like autocapture, session replays, error tracking, AIO, so on.
- Connect data sources
- Connect signal sources
- Scouts
- Bring you to PostHog to see the PRs flow
- **Ask questions along the way to customize this setup**

If we are fully committing to self-driving, this is the flow we'd want to implement.

Then there's cloud runs. This _is_ gonna be the fastest way to get to self-driving. Nothing beats a single-click setup that leads directly to a PR. This requires us to have that same autonomous experience, but with the questions to ask up front.

This default Wizard program isn't the right shape for a self-driving-first PostHog. 

### The Wizard assumes users want Product Analytics (and isn't in a monorepo)

What if they're not here for self-driving? Well, again, we need to ask.

PostHog has many ~products~ tools. The Wizard should ask the user which tool they want to use, then set it up for them.

If a user is here for AIO, why are we setting up 15 events for them?

We also don't handle monorepos well. We just assume the first front-end-client-side-shaped project is the one they want to instrument and set it up for them. In practice, agentic detection analytics shows that `22.2%` of users are using monorepos.

We don't handle any of these things well.

### The integration quality isn't that good anymore

Today, the Wizard does these things:
- Install the SDK
- Add environment variables
- Hook up identification
- Enable session replays, autocapture, and error tracking
- Adds ~15 events
- 5 insights and a dashboard.

When this was decided, it was exceptional because the benchmark to beat was an engineer reading our docs and adding the PostHog SDK, and then deciding what events to track and how to set up the dashboard.

The problem is, people have Fable now.

By comparison, the Wizard didn't leave projects in a ready to run state for [7/11 open source apps](https://github.com/PostHog/context-mill/pull/245#issuecomment-5024035756) that we ran against.

We leave behind many events like `viewed about page` and `clicked sign up`. We built simple insights and dashboards with these. 

There's also practical niceties like:
- A const file with all event definitions
- Event schemas
- Using PostHog through a wrapper (often the preferred shape)
- Group analytics
- Reverse proxies

Once again, these were great compared to an empty project and manual hookups. 

These are significantly less useful if you look at what someone with Opus 5 or Fable can do with our docs. 

## Why now, and why with urgency

I think we can and need to do this over the next quarter or so. 

### 1. Because we can
All the prep work to make this Wizard redesign possible is already done. 

I have strong belief that the orchestrated DAG based approach with mini agents can work. I have strong belief that the models are cheap enough and getting cheaper. We can afford to experiment and iterate quickly.

Also because, our ICP has shifted so much that we can afford to experiment. We can afford to drop some users on the floor and ship broken things.

### 2. Because we need to

Opus 5 is so cheap and so incredibly good at integrating PostHog. Give it the set of context we have and it will outperform the Wizard V2 in every way imaginable. 

Heck GPT 5.6 Sol High can do it 2x faster and half the speed, with slightly less depth.

The needs of a self-driving first integration also just looks different. We should be focused on suggesting better scouts, connecting signal sources, and giving PostHog's and the users' AI agents context.

Not doing a small set of place holder insights and events.

We're on the verge of slow obsolescence.

The target has shifted too far away from what we designed the V2 Wizard to do. 

The Wizard adapts, or we become obsolete.

## Two things, not one

There are two things in this RFC, not one.

The first is a **Wizard V2.5**. It's the immediate need. The default Wizard command does too much of the wrong thing, and most of the fix is subtraction. Same linear program, smaller job, new destination. It ships now.

The second is the **real Wizard V3**. It's a new substrate — orchestrated, modular, question driven. It ships over the rest of the quarter.

The line between them:

> **V2.5 is a fixed program, orchestrated across your projects, with one question.**
> **V3 is a planned program, where the work itself is chosen from what we find and what you tell us.**

Both orchestrate. Monorepos need orchestration and V2.5 has to handle monorepos, so the DAG ships now. The lockfile is one file, the root config is one file, a shared package has to land before the apps that consume it, and a server SDK is only useful when it agrees with the client on identity. You cannot fan four agents at one repo and hope.

What cutting the 15 captures, the insights, and the dashboards buys us isn't independence — it's a **fixed work list**. Install, initialize, identify, turn the features on. The same node types every run. The orchestrator has to figure out the shape of the repo and the order of the work; it doesn't have to decide what the work is.

That's the whole line. V2.5 discovers topology. V3 plans the program.

And because the work list is fixed, the only thing we have to ask is which projects. That's one question, and it renders the same in a terminal multi-select as it does in a web form.

Anything that needs a second kind of question, or needs the agent to decide what nodes should exist at all, is V3.

## Wizard V2.5 — what we're shipping immediately (like today, now)

### 1. Cut back what the default Wizard command does

- Install the SDK
- Initialize and apply environment variables
- Instrument basic identify
- instrument all of the base 4 products like Product Analytics, Web Analytics, Session Replay, AIO, and Error Tracking
- Enable all the features self-driving tries to enable.
- Write a handoff report for their agent locally, handoff to a handbook in PostHog
 - Suggest captures, funnels, dashboards, insights, etc.
 - Leave behind context for the agent to use the PostHog MCP
 - Suggest data sources to connect
 - Leave commands + links to skills to do things like add new data sources, upload source maps, etc.
 - **Key removals**: 15 capture sites, dashboards, insights. This isn't relevant, leave the tools for their agents to drive these.
 - **Advantage is speed**: All this work can be done fast enough where we don't lose their attention. I truly believe we can get this in 3-5 minutes tops.
 - **Not covered**: This is not the full V3 wizard. See the monorepo and cloud run scope below for what V2.5 does and does not do.

### 2. Force MCP install on the outro and cut out the rest

- It's Q3 2026 and we're self-driving. Of course they need this
- We don't need to ask, just install everywhere.
- I'm convinced we should ask about Slack and show the tutorial elsewhere

### 3. Last but not least, only handoff screen is: "Do you want self-driving?"

- On yes, we run that program immediately
- On Cloud run -> They could be taken to a web UI first experience
- We can teach them what this means with a show. We're good at shows.

### 4. New handoff

- If they say yes to self-driving, we open inbox
- If they say no, we open the notebook, where we advertise self-driving
- If they're on Cloud run, They can get a web UI first experience instead.

### 5. Handle monorepos

`22.2%` of runs are monorepos and we drop them on the floor today. This is where V2.5 needs real orchestration, and we should build it here rather than wait for V3.

- Detect every project, not the first front-end-client-side-shaped one
- Show the list and let the user pick which ones to instrument. This is the one question the V2.5 Wizard asks.
- Build a DAG over what they picked, and run it:
    - Root level work is serialized. The lockfile is one file, the root config is one file, and N agents racing on them is how you hand someone a broken repo.
    - Shared packages land before the apps that consume them.
    - The server SDK and the client SDK have to agree on identity, so they get planned together, not separately.
    - Everything genuinely independent runs in parallel, because otherwise a 4 project monorepo takes 4x as long and we blow the 3-5 minute target.
- One report covering all of them

The one thing we know up front and never have to infer is the project API key and host. Everything else about the shape of the repo is discovered.

**What keeps this V2.5 and not V3**: the node types are ours and they're fixed. Install, initialize, identify, turn the features on. The orchestrator works out the shape and the order — it doesn't decide what the work is. Deciding what the work is, is the planner, and the planner is V3.

### 6. A real cloud run

Cloud runs are the fastest way to get to self-driving and we should stop treating them as a later problem. In V2.5 they're nearly free, because a cloud run is self-driving by definition — the "Do you want self-driving?" question answers itself, and the only input left is which projects.

- `npx @posthog/wizard scaffold` ships, scoped hard to project detection. It emits the project list and what each project is, uploads it to PostHog, and exits. No surfaces, no evidence, no question set — those come with V3.
- The web UI shows the project picker. Same one question, different surface.
- The run replays headless through the existing hidden flag, with a one key answers file.
- It ends in a PR and the notebook.

---

All of this should take a week or two. Maybe we'll break a few things and drop a few people, but it's fine. We'll lose more people by not shipping this more relevant experience sooner.

## Wizard V3 — what we need to build next

1. Self-driving first experience
2. Customizable, modular setup
3. Option to defer to the user's agent
4. Higher instrumentation quality

### 1. Self-driving first experience

`@npx @posthog/wizard@latest` should do the following:
- Install the SDK
- Initialize it and hook up environment variables
- Identify your users
- Turn on all the features for self-driving
- Ask you about external signal sources
- Design and offer scouts to you
- Kick you to PostHog Desktop or the Inbox.
- Leave lots of useful context for _their_ agents to take over.
- A main agent surfacing questions and background agents doing while they are waiting for the user to respond.

For self-driving users, this is what's needed to get started. We can assume they're AI pilled, they have their own agents, and they are comfortable with using the PostHog through the MCP.

They don't need all the fluff on top. This _is_ just the thing we offer them.

For **cloud runs**, we can surface all of these questions early and during the run, and just pass this information to the agent.

This shape will change. Self-driving itself is fast changing. The new modular, multi-agent flows are flexible enough to adapt to these changes.

### 2. Customizable, modular setup

During onboarding, we already ask questions about which tools the user wants to use, what features they want to enable, and how they want to use PostHog.

We need to honor this.

Users in 2025 did not expect or understand this new, agent driven experience. By not asking them questions and giving them choices, we avoided confusion and got them off an empty page faster. 

This is no longer true, we can give them a better experience:

- (Agent) We scan your repo, ask you which projects to instrument (10s)
- (User) You tell us which projects and products you want to instrument
- (Agent) Plans the flow and enqueues agents to instrument your projects (15s)
- (Agent) We add and initialize the SDKs and hook up environment variables (30s - 1 min)
    - At this point, you can just leave and you'll have a working setup to continue with your agent. You _can_ just leave.
- (User) We pause after installing the SDKs, we ask you about features and teach you about them.
  - Do you want group analytics and what are the cohorts/groups you have? 
  - What questions are you trying to answer with your product analytics integration? 
  - Do you want to connect data warehouse sources? 
  - Do you want self driving? (Do you know what it is???)
  - Do you want some dashboards to start with?
  - Do you want us to install PostHog Desktop?
- (Agent) We move on to instrument what you agreed to, probably as you say yes or no to our tools. (3 minutes)
- (Agent) Then, once we're done, we ask to clean up after ourselves, review our changes, and leave context for your agent. This can take 5+ minutes. That's fine, leave us running, we'll handle the rest.

### 3. Option to defer to the user's agent
We cannot really compete with Fable class models. That's fine. What if we offer that as an option? A basic installation.

There are things we can do for you still:
- Install
- Environment variables
- Enabling features
- Hooking up identification (I'm convinced _we_ can do this uniquely lol)
- Leaving skills for your agent
- Leave meaningful instructions as handoff.

### 4. Higher instrumentation quality
 
What do you care about?

Yes you, the user.

Have no opinions? We'll scan your repo, hook up events for the core flows (and more than before) and set up insights and dashboards. Even leave suggestions for your agents.

Have opinions? You mainly care about sign up conversion and time to checkout? We can do that for you, too.

We'll finish with a GPT 5.6 Sol class audit. This, alone, turns 4/11 projects capturing successfully post instrumentation after a wizard run to 11/11. In our tests, this gives us 13% higher ingestion rate after a Wizard run in the same period.

We can do this because GPT 5.6 Sol class models are faster, cheaper, and more capable than anything practical before.

#### The run — questions while we work

Work starts the moment projects are confirmed — SDK install, init, env vars, identification need no plan and no questions. Everything after that happens on one split surface: the left pane asks, the right pane works. This is the "main agent surfacing questions, background agents doing" shape made literal: questions run concurrent with the work instead of pausing it, so the time a user spends answering is time agents are already building. When no question is queued, the left pane shows the teaching slides.

The todo chain is the self-driving flow itself:

- Install the SDK (across every selected project)
- Initialize it and hook up environment variables
- Identify your users
- Turn on all the features self-driving feeds on — session replay, error tracking, logs, AI observability when we see LLM calls, support
- Connect GitHub
- Ask about external signal sources — and suggest every one the exploration found evidence for (Sentry in the deps, Linear links in the README, an `openai` import)
- Design and offer scouts (propose-first, never created without approval)
- Audit our own work end to end — the pass from "Higher instrumentation quality" above
- Write the report, leave context for _their_ agents, kick to Desktop or the Inbox

Question rules come from the setup skill's ground rules: the decline option is always first (an accidental enter skips, never commits) — except the GitHub gate, the one step the run genuinely waits on, where the affirmative goes first and the todo pane says so.

#### When we stop — friendly aborts

The setup skill defines three verbatim abort cases; the wizard catches them and renders an explanation instead of a stack trace. The rules of a good abort: say why we stopped, show what survives (work done is never rolled back), and leave the exact way back in.

```
 PostHog Wizard v3.0.0                                            Feedback: wizard@posthog.com


        ◆ We stopped — GitHub wasn't connected

        Self-driving can't research findings or open PRs without the
        GitHub App, so we stopped before the signal-source setup.

        Everything done so far is yours to keep:

           ✔ SDK installed · apps/web, apps/mobile
           ✔ Env vars wired
           ✔ Users identified
           ✔ Features on · replay · errors · logs

        Pick it back up anytime:

           github.com/apps/posthog      install the app first
           npx @posthog/wizard          resumes where we stopped

             ▸ Exit


 ──────────────────────────────────────────────────────────────────────────────
  enter exit
```

Same shape, different copy for the other two:

- `self-driving is not available for this project` — "Self-driving isn't available on this project yet." Keeps the integration work, points at the notebook report, offers the agent-handoff path so the run still ends with value.
- `requires-interactive-mode` — headless runs only: a question came up that the answers file couldn't cover. Exits non-zero with the unanswered question ids on stderr, so the cloud pipeline can re-render the form instead of guessing.

#### Cloud runs — scaffold and replay

Cloud runs split the wizard into two halves around the human. First, `scaffold`: a machine-only, run-and-done command the sandbox executes in the repo checkout. It explores, builds the structured question set, uploads, exits — no human ever runs it, no TUI.

```
$ npx @posthog/wizard scaffold

[scaffold] wizard 3.0.0 · project 2 · token from env
[scaffold] exploring /repo                       monorepo · pnpm workspaces
[scaffold] projects: 4                           apps/web apps/mobile services/api packages/ui
[scaffold] surfaces: identify groups error-tracking logs ai-observability mcp-analytics revenue data-sources
[scaffold] evidence: sentry(deps) openai(imports) stripe(deps) postgres(prisma) orgs-table(schema)
[scaffold] questions queued: 12
[scaffold] uploaded: scaffold 019f8c4a to us.posthog.com
[scaffold] done                                  exit 0
```

The scaffold's questions render in the PostHog UI as **one form** — the same asks the TUI surfaces iteratively, answered in one sitting because the human is in a browser, not a terminal. Same question schema (`kind` / `evidence` / `suggested` / `declineFirst`); the TUI drains the deck iteratively, the cloud form collects it wholesale.

A sketch of that form (PostHog UI, not the TUI):

```
◆ Set up self-driving — acme/monorepo                    answer once, we'll open a PR

  Projects        ◼ apps/web   ◼ apps/mobile   ◻ services/api   ◻ packages/ui
  Group by        ◼ organization                        `organizations` table found
  Signal sources  ◼ Sentry (in your deps)  ◻ Linear  ◻ Zendesk  ▸ 34 more
  AI observability◼ wrap openai + anthropic calls in services/api
  Scouts          ◼ Checkout funnel watch   ◼ Signup quality     drafted for you
  Dashboards      ◻ start me off with core flows

                                                        [ Run it — PR when done ]
```

Then the replay half: the cloud agent runs the wizard under the existing hidden headless flag, feeding the collected answers back in. Every `wizard_ask` resolves from the file instead of a human.

```
$ npx @posthog/wizard --headless-DONOTUSE-EXPERIMENTAL --answers ./answers.json

[wizard] ⚠ EXPERIMENTAL — do not use. Unstable, subject to breaking changes.
[wizard]   This is the substrate under cloud runs. Humans: run without flags.
[wizard] scaffold 019f8c4a · 12 questions · 11 answered · 1 defaulted to decline
[wizard] answers validated against question schema
[wizard] install sdk · apps/web                  done
[wizard] install sdk · apps/mobile               done
[wizard] init + env vars                         done
[wizard] identify · lib/auth.ts                  done
[wizard] features · replay errors logs aio       done
[wizard] github                                  already connected
[wizard] signal sources · sentry linear          done
[wizard] scouts · 1 of 2 approved in answers     done
[wizard] report + handoff                        .posthog/report.md
[wizard] done                                    exit 0
```

The answers file — ids match the scaffold's question ids, values validated against each question's `kind`:

```json
{
  "scaffold": "019f8c4a",
  "answers": {
    "projects": ["apps/web", "apps/mobile"],
    "groups": "organization",
    "signal-sources": ["sentry", "linear"],
    "ai-observability": true,
    "scouts": ["checkout-funnel-watch"],
    "dashboards": "decline"
  }
}
```

Semantics worth pinning:

- **Missing answer = decline, loudly.** Decline-first isn't just option ordering — it's the headless default for anything unanswered. A silent gap never opts anyone into something.
- **Stale answers fail hard.** Answers are validated against the referenced scaffold; a stale scaffold id is a hard fail, no fuzzy matching.
- **One question engine, three surfaces.** TUI iteratively, cloud form wholesale, headless replay. `wizard_ask` doesn't know which one it's talking to.
- The flag keeps its ugly name, hiding, and warning copy — the pipeline isn't magic, but humans stay off it.
